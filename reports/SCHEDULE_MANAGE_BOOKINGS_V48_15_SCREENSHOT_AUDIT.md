## Behavior and backend boundaries

- **Access:** new schedule-event endpoint checks both `schedules.view` and `bookings.view_all`, applies `Policy.bookingAllowed` to every booking, and uses private/no-store response headers. It never emits passenger phone numbers, other operators' bookings or unrelated PNRs.
- **History:** database lacks exact historical block->release->confirm times for some external records. `recorded` means a booking's actual `booked_at`, not an invented block date. Only real `cancelled_at`, `expired_at`, `confirmed_at`, and manual seat-block timestamps become separate events. “Blocked (active)” uses actual stored manual blocks and should not imply a reconstructed historical snapshot.
- **Seat map and counters:** visual layout derives from live source seat geometry; blue/pink/white represent source statuses, not screenshot sample colors applied blindly; per-seat `×N` badge uses counted active reservations when available.
- **Cancellation:** existing schedule bulk-cancellation logic is retained; selections are passenger-seat scoped, subject to booking access and cancellation permissions. The app does not automatically cancel merely by opening the popup.
- **Printing/importing:** existing `PickupChartV40.openPrint/openImport` continues the permitted current GDS PDF and reference import flows; no booked inventory is overwritten by an imported chart.
- **Notify:** dropdown contains Ticket Confirmation, Bus Details, Bus Delay/Early and Bus Cancellation. The first two use existing permitted templates; Delay/Early composes a validation-checked custom message and Cancellation composes an explicit informational message. These create *records* with `delivery_verified:false`, not proof of WhatsApp/SMS delivery. A cancellation message does not cancel/refund a ticket.
- **Delay/Advance:** signed minutes validated [-720,+720]; reason required; back end updates only schedule-specific stages not already reached. Reapplying the same adjustment is idempotent (uses delta), and arrival-day rollover is tracked; route template remains unchanged. The service can't be completed/cancelled. Existing timetable changes and audit remain recorded.
- **Live GPS:** no animation, fake speed, route polyline, StreetView or real-time provider telemetry is invented. Map requires latest valid coordinates in the backend; tiles depend on internet availability.
- **Cities:** Via-City origin/destination toggles and subroute percentages are saved as UI preferences only. Published route slot CRUD remains the Routes editor, not the screenshot stub.

### Visual/operational qualification
The screenshots are reference images, not production system state or evidence of exact SaveTrip backend behavior. CSS is screenshot-calibrated, not certified pixel-by-pixel. In particular, server data cannot truthfully reproduce the screenshot's historical timeline durations, booking counts, fare badges and GPS unless that evidence exists in the GDS. Manual desktop/mobile browser comparison, real operator/OTA data UAT, GPS telemetry accuracy, notification provider delivery, and payment/refund operational tests are outstanding for production certification.
